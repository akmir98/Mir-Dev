Building My First REST API

I'd used plenty of REST APIs before — fetching data, handling loading states, dealing with the occasional 500 error at 2am. What I hadn't done was build one from the other side. So I set myself a small, deliberately boring project: a task list API. Nothing clever, just enough surface area to actually learn something.

Starting smaller than felt necessary

My first instinct was to plan out the "real" version — auth, validation, pagination, the works. I'm glad I didn't. I started with four routes and no database at all, just an array in memory:

  • GET /tasks — return everything
  • POST /tasks — add one
  • PUT /tasks/:id — update one
  • DELETE /tasks/:id — remove one

That was enough to learn how Express actually routes a request, how middleware sits in between, and how easy it is to send back the wrong status code without noticing (I returned 200 for a failed lookup more than once before I started paying attention).

Where it got genuinely interesting

Swapping the in-memory array for a real database was the point where this stopped feeling like a tutorial and started feeling like the actual job. Suddenly I had to think about schema design, what happens on a duplicate request, and why my "delete" route kept succeeding even when the task didn't exist (spoiler: I wasn't checking).

The frontend habit that helped most here, unexpectedly, was thinking in states. A request isn't just "success or fail" — it's loading, success, empty, and several different flavors of error, the same way a UI component is. Modeling backend responses that way made the whole thing click faster than I expected.

What I'd tell past-me

  • Test with a real HTTP client (Postman, Thunder Client, curl) before you trust anything.
  • Log the request body before you debug anything else — half my bugs were "the data wasn't shaped the way I assumed."
  • Status codes matter more than they seem to at first. Get in the habit early.

It's a small project. It won't impress anyone on its own. But it's the first time I've built something where the frontend was the easy part — and that felt like a genuinely useful milestone to write down.
